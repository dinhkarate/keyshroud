Secrets for AI coding agents

Your agents use the keys. They never see them.

keyshroud keeps API keys in an encrypted vault on your machine (or your own Vaultwarden, or the secret manager your team already runs) and injects them into the commands your AI coding agent runs. Any secret value that shows up in tool output is replaced with <redacted:NAME> before the model reads it.

$npm i -g keyshroud

The problem

A key only has to be printed once

Whatever an agent reads goes to the model provider and stays in the transcript. These are the usual ways a key gets there, and what keyshroud does about each.

Agents read it to debug. .gitignore stops commits, not reads.

Printed on failure

A failed command

Claude Code cannot rewrite the output of a command that fails, so a hook alone leaves it unmasked. keyshroud claude-guard makes Claude Code start its shell through a small launcher that masks what the command prints as it is written, and keeps its exit status. Quickstart

Up and running in three steps

You need Node.js 18.19+. No account, no server: the first secret creates an encrypted vault on your machine.

Install

npm i -g keyshroud

One CLI that agents call from their shell, plus plugins for Claude Code and pi. An MCP server covers clients without a shell.

Store a secret

keyshroud add --env GH_TOKEN \
  --item "GitHub token"

Typed into a masked prompt, or a dialog when an agent starts it. The vault’s key goes to the macOS keychain, the Linux Secret Service or Windows DPAPI. Already have a .env? keyshroud import moves it.

Use it

keyshroud run -- gh auth status

The command gets the token; what it prints shows <redacted:GH_TOKEN>. In Claude Code, install the plugin: /plugin marketplace add dinhkarate/keyshroud

Or let your agent set it up

Paste this into Claude Code, Codex, Cursor, OpenCode or pi. The agent follows install.md and leaves typing secrets (and any vault password) to you.

Read https://keyshroud.dev/install.md and set up keyshroud for me.

Features

Built for agents, not just shells

Every feature works with names and references, never with values.

Masked output

keyshroud run streams stdout and stderr through a redactor. A secret that arrives split across two chunks is still masked. Masking is always on, in a terminal too, because some agents run commands on one; --no-mask hands the terminal to an interactive program. Output that is not text passes through byte for byte.

Hooks on tool output

pi tool_result and Claude Code PostToolUse hooks scrub tool results, including commands the agent ran without keyshroud.

The guard

Claude Code can't rewrite a failed call, so keyshroud claude-guard masks what every Bash command prints as it is written, failed ones included.

MCP server

For clients without a shell, keyshroud mcp gives them secrets_run, secrets_list and secrets_request. None of them return values.

Committable references

Write GH_TOKEN=keyshroud://GitHub token in a .env.refs file you can commit. keyshroud import converts an existing .env.

Paste-to-create

When an agent needs a new key it runs keyshroud add, and a hidden-input dialog opens on your desktop. You paste; the chat never sees it.

Inject & scan

inject renders {{ keyshroud://… }} templates into files only you can read (mode 0600). scan finds leaked values in your repo before you commit.

A project's own secrets

A .keyshroud.json in a repo, such as { "only": ["STRIPE_*"] }, narrows what keyshroud run and the agent get there to the names that project needs.

Names-only audit log

audit.jsonl records which names were used, when and by which command, so you can see what an agent reached for. Never a value.

Least privilege

Give each project only its own keys

By default a command gets every wired secret. Narrow that per project or per command. These are defaults against accidents, not walls: see the threat model.

Per project

A scope file in the repo

In that directory, keyshroud run, the MCP tools and the names an agent is told are narrowed to the names in scope. Masking still covers every value.

$ keyshroud scope --only 'DB_*,ACME_*'
$ keyshroud run --only GH_TOKEN -- gh auth status
Secret unresolved: GH_TOKEN is outside this project's scope (~/acme-app/.keyshroud.json)

Name what a command needs

--only gives a command just the names you list. With Vaultwarden, keyshroud setup gives agents an account of their own, so they never open your whole vault.

Compare

Four ways to give an agent a secret

The tools in this space take one of four approaches. keyshroud masks what the model reads whether or not you wrapped the command, and keeps the vault on your side.

ApproachDoes the model see the value?A command you did not wrapCovers
Names in, masked output out
keyshroud		 No. Tool output is masked. Masked too in Claude Code (hook, plus the guard for failed commands) and pi/omp. Other agents rely on keyshroud run. Any secret a command reads from its environment or a file. Free, MIT, no account.
A wrapper that masks its own child
1Password op run, dotenvx run --redact, varlock run, secretspec run		 Not from the wrapped command. Not masked. The same, for the commands you wrap. op run needs a paid 1Password account.
A vault MCP server
Bitwarden MCP, HashiCorp Vault MCP, Doppler MCP, Infisical MCP (by default)		 Yes. The tool returns it. Not masked. Looking a secret up, with the value in the context from then on.
An egress proxy with placeholders
Infisical Agent Vault, OneCLI, fnox proxy, 1Password for NVIDIA OpenShell, Claude Code’s sandbox.credentials mask		 No. The agent holds a placeholder. Nothing to mask: the real value is never in the shell. HTTP(S) credentials for hosts you allow. Needs a proxy that can read the requests.

An egress proxy is the stronger tool against a hostile or prompt-injected agent, for the credentials it covers; keyshroud also covers database passwords, SSH and signing keys and every CLI that reads a variable. They combine. As we read each project’s documentation on 2026-11-15; corrections are welcome in an issue.

Security

An honest threat model

Redaction is defense in depth, not a sandbox. Every guarantee we test for and every known limit is in the security model.

Protected

  • Secret values entering the model's context through tool output, a failed command’s included (in Claude Code, with keyshroud claude-guard on)
  • Secrets at rest: the local vault is AES-256-GCM, its key in the OS keychain
  • Secrets pasted into chat while being stored (keyshroud uses a masked prompt instead)
  • Plaintext in agent config and auth.json (only references are stored)
  • Secret values accidentally committed to your repo (caught by keyshroud scan)

Not protected

  • A malicious or prompt-injected agent that encodes a value or sends it over the network
  • Other programs running as your user: they can read the vault’s key from the keychain (create the vault with a passphrase to be asked instead)
  • In Claude Code with the guard off: what a failed command prints, unless it ran through keyshroud run (the hook can’t rewrite a failed call)
  • A project scope and the guard are defaults against accidents, not walls: a program running as you can change them
  • Values shorter than 6 characters (not redacted, to avoid noise)

FAQ

Questions people ask first

The long list, with CI, Docker, Windows and upgrading, is in the FAQ.

Do I need Vaultwarden or any server?

No. Secrets live in an encrypted file on your machine by default, with its key in the OS keychain. Vaultwarden or Bitwarden is optional, for the same secrets on several machines.

Can the agent still use the key?

Yes. The command gets the real value in its environment; only the text the model reads is masked.

Is this a sandbox?

No. It stops accidental disclosure. A hostile or prompt-injected agent can still send a value it can use somewhere else; for that threat use an egress proxy with placeholder credentials and keep a human approving commands.

Doesn’t Claude Code do this itself?

Partly, and differently. Claude Code can deny reads of files such as .env, and its sandbox can show a command a placeholder for a credential and put the real value on requests to hosts you allow. It has no secret store and does not rewrite what a tool prints. keyshroud is the store, works the same across agents, and masks output; the two combine.

Why not just .gitignore my .env?

That stops commits, not reads. Agents read .env to debug, and whatever they read goes to the model provider.

We use HashiCorp Vault, AWS or 1Password at work. Do I have to move the secrets?

No. keyshroud reads them where they are, with the sign-in you already have, and never writes there.

Does it work on Windows?

Yes, tested on Windows 10 with Node 22. The local vault keeps its key with DPAPI. The guard for failed commands is macOS and Linux only.

Stop pasting API keys into chat

Every key you paste lives on in the transcript, the provider’s logs and every future context window. Give your agent the name instead.
